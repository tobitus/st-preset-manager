## 1. New document schema (exact field names)

### 1.1 Loadouts (`doc.loadouts[lid]`)
```
{
  id: string,                      // == key
  name: string, notes: string,
  kind: 'root' | 'playstyle',
  parent: null | string,           // null iff kind==='root'; else a lid whose kind==='root'
  enabled: { [leafId]: boolean },  // root: COMPLETE (every leaf, validateDoc enforces)
                                   // playstyle: SPARSE (only explicit sets; absent = inherit)
  overrides: { [modelName]: {
      enabled: { [leafId]: boolean },   // sparse, as today (store completeOverride on write)
      tuning: null | string              // named tuning of that Model; null = Model's defaultTuning
  } }
}
```
- `doc.activeLoadoutId` may point at either kind. `doc.tuningOverrides` is REMOVED (schema fails on its presence after upgrade: `validateDoc` → `tuningOverrides (removed)`).
- Invariants enforced in `validateDoc` (shared/schema.js:42-128 [read] currently checks `id/name/notes/enabled/overrides` and "active loadout covers every leaf"): (a) `kind` ∈ {root, playstyle}; (b) root ⇒ `parent === null` and `enabled` has every leaf of `iterLeaves`; (c) playstyle ⇒ `parent` names an existing loadout **of kind root** (no chaining — a parent whose kind is playstyle fails `loadouts.<lid>.parent (parent must be a root)`); (d) every key of a playstyle `enabled` and of every `overrides[*].enabled` is a known leaf id; (e) at least one root exists; (f) `overrides[*].tuning` is null or a non-empty string (registry cross-check is NOT in validateDoc — it has no registry; see compile).

### 1.2 Model registry (`models.json`, `reg.models[name]`)
```
{ id, name, matches, profiles, preferredProfile,       // unchanged
  tunings: { [tuningName]: { ...TUNING_KEYS subset } }, // ≥ 1 entry
  defaultTuning: string }                                // must be a key of tunings
```
`tuning` (singular) is REMOVED. `validateRegistry` (schema.js:166-199 [read]) enforces: `tunings` object, every value TUNING_KEYS-only, non-empty, `defaultTuning ∈ keys(tunings)`. `seedFromProfiles`/Settings-tab new Model create `tunings: { default: {} }, defaultTuning: 'default'`.

### 1.3 Old-document conversion (decision: convert on load, no file rewrite until the next save)
- `shared/schema.js` gets `upgradeDoc(doc)` (pure, idempotent): every loadout lacking `kind` → `kind:'root', parent:null`, `ensureAllLeaves` on it; every override lacking `tuning` → `tuning:null`; `delete doc.tuningOverrides` (the values are dropped — owner: no migration needed; the pre-save revision snapshot written by `_savePresetNow` (store.js:505-508 [read]) preserves the old bytes on the first save after upgrade). `upgradeRegistry(reg)`: `tuning` → `tunings:{default: tuning}, defaultTuning:'default'`.
- Call sites: `store.rescan` right after `deriveStructure/stripLeafEnabled` (store.js:313-315 [read]); `importPreset` native branch (store.js:421-425 [read]); `PUT /presets/:id` (native save — find the route; [INFERENCE] it validates then saves); registry load in `store.init` (store.js:134 [read], the models.json read — builder to locate) and `PUT /models`.
- Acceptance: a 2c12a40-format document (one loadout, `tuningOverrides` non-empty) loads with no error, `validateDoc` passes after `upgradeDoc`, the loadout is a root, `compile` output's `prompt_order` is byte-identical to the pre-upgrade compile for a null Model; the first `_savePresetNow` writes a revision whose `doc.tuningOverrides` still holds the old values.

## 2. Inheritance resolution (new `shared/loadouts.js`, browser-safe like groups.js)

```
effectiveEnabled(doc, loadoutId, modelName|null)
  → { enabled: {[id]: bool}, source: {[id]: 'root'|'loadout'|'override'} }
  1. L = doc.loadouts[lid] (throw CompileError-compatible error when missing)
  2. R = L.kind==='root' ? L : doc.loadouts[L.parent]   (missing/non-root parent → error)
  3. enabled = {...R.enabled}; source[id]='root' for all
  4. if L.kind==='playstyle': for [id,on] of L.enabled → enabled[id]=on, source='loadout'
  5. if modelName && L.overrides[modelName]?.enabled: apply, source='override'
  6. groups.normalize(doc, enabled)  (unchanged safety net)
```
A root's own `overrides` are applied in step 5 when L is that root. A playstyle NEVER sees its parent's `overrides` (decision below).

`compile(doc, model, base, loadoutId, opts)` (compile.js:34-156 [read]) becomes:
1. unchanged (base ⊕ settings).
2. **Tuning**: `T = model ? model.tunings[(L.overrides[model.name]?.tuning) ?? model.defaultTuning] : {}`; a `tuning` name absent from `model.tunings` throws `CompileError("loadout <lid> override for <M> names unknown tuning <t>")` — same loudness as the existing missing-loadout throw (compile.js:67 [read]); the delete/rename routes below make this unreachable via the API. `out ⊕= T` over TUNING_KEYS.
3. `enabled = effectiveEnabled(doc, lid, model?.name).enabled`.
4–5 unchanged. `exportSt` unchanged (null Model → root ⊕ playstyle only). Header comment rewritten.

## 3. Decisions on the open points

| Point | Decision | Rejected alternative / why |
|---|---|---|
| Root carries per-Model overrides? | **Yes**, same `overrides` field and mechanism. A child does not inherit its parent's overrides. | "Overrides only on playstyles" would force the owner's stated real workflow ("settle once, vary per Model", roadmap 016) through an extra playstyle layer he does not want. Roadmap 016 says overrides stay "inside each loadout". Not inheriting parent overrides keeps exactly three layers, no chaining. |
| Delete a root with children | **Refused, 409** `root "<name>" has N playstyle loadout(s); delete or re-parent them first`. The "never the last loadout" rule (routes.js:602 [read]) becomes "never the last root"; a playstyle is always deletable. | Cascade delete silently destroys work; auto-reparent to another root silently changes what children mean. |
| Convert root → playstyle | `PATCH {kind:'playstyle', parent}`: refused 409 while it has children; else `enabled` becomes the sparse diff against the new parent (only keys whose value differs), so the effective map is unchanged. Convert playstyle → root: `PATCH {kind:'root'}` materialises `effectiveEnabled(doc, lid, null)` as the complete map, `parent=null`. Re-parent playstyle → other root: `PATCH {parent}` keeps the explicit sets. | Dropping explicit sets on conversion loses edits with no visible cause. |
| New blocks (addBlock/addOption/addSection/copyBlock/copyIntoDoc; docops.js:376,517,581-584,918 [read]) | Every **root** gets `false`; `addSection` also sets `true` in the ACTIVE loadout (explicit set if it is a playstyle). Playstyles get **no** entry (inherit). `deleteBlock` keeps deleting the key from every loadout and override (docops.js:630-633 [read]). | Writing `false` into playstyles would turn every new block into an explicit override in every child. |
| ST panel write-back (slot.js:169-212 [read]) | Enabled bit → the per-Model override when it already controls the id (unchanged), else the **desired loadout's own layer**: root → its complete map (+ `normalize`); playstyle → explicit set in its sparse map (+ `completeOverride`, as overrides do today). Never into the parent. Tuning key → the Model's tuning **in effect** for this compile (`L.overrides[M]?.tuning ?? M.defaultTuning`) in the registry; `globalTuning` becomes `tuningWrite: {name, values}`; no Model → `doc.settings` + warning (unchanged). | Routing a playstyle tick into the root would silently change sibling playstyles — the global-in-scoped-system bug. |
| Named-tuning deletion/rename | DELETE a tuning: 409 if it is the default or referenced by any `loadouts[*].overrides[M].tuning` across the library; rename migrates references in one `_commit` with a labelled revision (pattern: `renameModel`, store.js:905-933 [read]). `models_rename`/`merge` migrate `overrides` keys as today, drop the `tuningOverrides` branch; merge unions `tunings` by name (first-listed wins), `defaultTuning` from the first-listed. | Dangling refs would surface only as a compile throw. |
| Outline shows which loadout? | The **picker's** loadout (`view.picker.value`), not only the active one. `buildOutline(doc)` is today called without a loadout id (ext/tabs/outline.js:575 [read]) so the outline always shows the ACTIVE loadout while the model panel already follows the picker (presets.js:384 [read]). `toggle`/`setGroup` gain optional `loadoutId` (default active). | Keeping "outline = active" means editing a playstyle requires activating it first, which also moves what ST runs. Flagged as a UI-taste call for the owner in §6. |
| Undo scope (note item 52) | **Server-side, per preset, in-memory undo/redo stacks of whole-document snapshots**, pushed by every `_savePresetNow` on an existing document (ops, loadout/override/meta routes, ST-panel write-backs), cap 100. Whole-document swaps (`_replaceDocNow`: import replace, restore) clear both stacks. Undo/redo themselves go through the `_replaceDocNow` body with labels `undo`/`redo` so the slot-changed marker + desired-loadout fallback apply (store.js:536-560 [read]). Registry (models.json) changes are NOT undoable (document-scoped feature). Lost on plugin restart — documented. | Client-side inverse ops: no inverse exists for `deleteBlock`, `copyBlock`, multi-step `moveLeaf`, panel reorders; coverage would be partial. Revisions: coalesced 5 min (store.js:698-701 [read]) so a burst is one step — too coarse for undo. |
| F-066 import | In `importStPreset` (recognizers.js:748 loop [read]): if `prompt_order` has both `character_id` 100000 and 100001, skip 100000 and push `"dropped prompt_order 100000: ST chat completion reads only 100001 (F-066)"` into `source.recognizer.notes`. Only this pair; other ids unchanged. | Dropping every non-100001 entry would change fixtures that legitimately carry other ids. |
| Block numbers (item 51) | Display-only `.pm-row-num` = 1-based position of the leaf in `flattenSeq` order of its sequence (headings included); `data-pos` on the `li`. | Numbering only blocks or only ST-visible prompts diverges from the outline the owner is looking at. Taste call → §6. |
| Headerless group row (item 47) | Selectable: `li[data-kind=group][data-key='']` gets `data-key = node.key` (`grp:…`); selection model allows a group key; editor pane shows a group card (name input → `renameGroup`, 1/N → `setCardinality`, **Dissolve** → new op `dissolveGroup {key}` = promote every option in place, options keep their enabled bits, atomic). | N client `promote` calls = N revisions and a half-dissolved group on failure. |
| Multi-select promote/demote (item 50) | Ctrl/Cmd-click adds to a `Set<string>` selection (Shift = range within the visible list); `promote`/`demote` accept `keys: string[]` (document order, all-or-nothing, single revision). `key` stays accepted for one. | One request per row = N revisions and partial failure. |
