## 0. Findings per report (what the code does today)

### Report 1 — no Fork in the interface
- Route exists and is complete: `plugin/routes.js:450-547` **[read]** — `POST /presets/:id/fork {name, folder?, tags?, notes?}` → `201 {doc, rev}`; deep copy, new `p_` id, every block identifier re-minted and leaf refs/ghosts re-pointed, loadouts re-keyed with new ids, active loadout preserved by position, `source.forkedFrom = src.id`, name conflict → 409 `name "<x>" is already taken`. Exercised by `dev/check-phase5.mjs:427` (REST only) and mapped by MCP `preset_fork` (`mcp/server.js:36`).
- The Library row renders exactly `Open`, `Load`, `Delete` (`ext/window.js:406-411` **[read]**); nothing calls `/fork` from `ext/`. `Delete` is the pattern to copy: ST `callGenericPopup` → `bridge.edit(() => api(...))` → `onChange()` (= `refresh`) with `.pm-error` prepended on failure (`window.js:418-436`). `onOpen(id)` switches to the Presets tab and opens the preset (`window.js:196-199`).

### Report 2 — "no path from a section heading to a selection group"
- `Make group heading` on a **section heading is refused**: `headingAction(doc, key, 'group')` returns `refuse: 'Make group heading works on a plain row — make it a plain row first'` for any rank other than item/group (`ext/outline-model.js:287-290` **[read]**); the rank bar greys the button with that title (`ext/tabs/presets.js:878-893`).
- `Make group from selection` refuses a section heading outright: `opCreateGroup` (a) `a section heading cannot become a group member — unmake the section first` (`shared/docops.js:498-500` **[read]**), and a row already at rank group/option (`:501-505`), non-adjacent rows (`:508-511`).
- The ladder op **does** go section → group directly: `demote` on rank `section` sets rank `group` with gmeta from the stash or `{name: label, cardinality: 'pick-one-or-more'}` (`shared/outline.js:331-343` **[read]**); the rows that were the section's children stay items (rank untouched), i.e. the result is a **headed group with zero options followed by plain rows**, and the rows rejoin the enclosing section/top level (`rebuildSeq`, `outline.js:138-173`). The `Demote` button / Shift+Tab is wired to it (`presets.js:325`, `rankOp` `:555-563`) but nothing labels it as "turn into group".
- Today's working paths, both undiscoverable: (i) select heading → **Demote** (section→group) → select the rows below → **Demote** (item→option: `rebuildSeq` attaches options to the open group above, `outline.js:154-166`); (ii) **Unmake section heading** (`unmakeSection`, `outline.js:405-415`) → Ctrl-click heading + rows → **Make group from selection** with the heading as header.
- An **empty headed group is already valid and reachable**: `rebuildSeq` keeps a group whose `header !== null` even with `options.length === 0` (`outline.js:110-118` **[read]**: only a header-less, option-less group is dropped); `validateDoc` requires `options` to be an array, not non-empty (`shared/schema.js:177-190` **[read]**); `groupNode` renders zero options (`ext/outline-model.js:157-170`); `promote` on the last plain row produces one today. **[INFERENCE]** compile/`normalize`/`completeOverride` on an empty pick-one group do not throw — chunk 4 pins this with a unit test.

### Report 3 — "heading at the very end, block before the selected row, can't move the block under the heading"
- **Both UI inserts send `before: <selected row>`** and both ops insert at the anchor's flat index: `insertSection` → `{op:'addSection', before: selected}` (`presets.js:744-751` **[read]**), `insertBlock` → `{op:'addBlock', before: selected}` (`:754-757`); `opAddSection` splices the heading at `anchor.idx` (option anchor → `snapAboveGroup`) (`docops.js:754-795` **[read]**), `opAddBlock` at `anchor.idx` with the anchor's sname (`:691-737`). Only `before: null` (nothing selected) appends to the end (`:782-786`, `:723-727`). `dev/check-fix1.mjs` f1 (`:372-405`) and f8 (`:577-597`) verified "directly above the selected row" through the real UI on 2026-09-29.
  → **Hypothesis H1 (unverified):** the heading went to the end because nothing was selected at that moment (Insert tooltip: "at the selected row (or at the end)", `presets.js:336`). A selection on a headerless group row (`grp:` key) would instead give a 404 in the status line (`docops.js:770`), not "end". Step 1 of chunk 2's check reproduces both cases before anything changes.
- **Moving a block into an empty section is impossible today**, by three independent rules:
  1. Drag: jQuery UI sortable is per `ul.pm-list` with no `connectWith` between outline lists (`ext/tabs/outline.js:635-662` **[read]**); a drag is diffed into one `moveLeaf {delta}` among the SAME list's siblings (`dragOps`, `outline-model.js:321-328`). An empty section's `ul` has no items and no height (`style.css:264-268`), so it is never a drop target.
  2. `moveLeaf` treats a section heading as a wall for items/groups: moving down when the next block starts with a section heading → `cannot move below the section (bottom of it)` (`shared/outline.js:542-544` **[read]**); moving up across the heading → `cannot move above the section heading (demote the section first)` (`:522-530`). Doc comment `:466-480` ("Sections are move limits", v1 parity).
  3. `addBlock` anchored ON a section heading lands **outside, above** the section (`docops.js:712-716`, `test/docops-fixes.test.js:182`); and an empty section has no inner row to anchor on.
  The only way in today is a shelf drop (`insertEntries` anchored on a section heading → `at = i + 1` as item, `outline.js:586-588`) or `addBlock` with `before` = the first row AFTER the empty section / `null` when the section is last (rebuild puts the item under the preceding heading).

## 1. Decisions

| Point | Decision | Rejected / why |
|---|---|---|
| **Insert placement** | **After** the selected row, for both inserts: new `after: <leafKey>` argument on `addBlock` and `addSection` (exclusive with `before`; `before` kept for REST/MCP and the existing tests/checks that use it: `check-mini.mjs:286`, `check-round3.mjs:464`, `test/fix1-addsection.test.js`). The UI sends `after: selected ?? null` (`null` = end, unchanged). Why after: (i) `runInsertOp` selects the new row (`presets.js:765`), so repeated inserts chain **downward** in reading order (with `before` they stack upward, reversed); (ii) `Duplicate` already lands "directly below" (`copyBlock … after: g.key`, `presets.js:777`) — one rule for all three; (iii) it is the fix for report 3's second half: select the new heading → Insert → Block lands as the heading's first row, no move needed. | Keep `before` and only fix the end case: leaves the heading/block asymmetry the owner sees. |
| **`after` landing rules** (server side, in `docops.js`, mirrors the drop rules of `insertEntries`, `outline.js:560-598` **[read]**) | **addBlock after**: plain item → directly below it, same section; **option** → the next option of that group (rank option, anchor's gmeta); **group heading** → its first option (as a drop ON the heading, `outline.js:582-585`); **section heading** → first row inside the section (as `outline.js:586-588`); a `grp:` (headerless group) selection → the UI resolves it to the group's last option key, so the block joins that group last. **addSection after**: item → directly below it (rows from there to the next heading become its children — today's mid-section split shifted one row); **option / group heading** → after the whole group (sections never split a group; mirrors `snapAboveGroup`, `docops.js:965-969`); **section heading** → after the whole section (a sibling section; nesting is out of scope). | Computing the anchor in the UI (`before` = next row): the UI would need `blockAt`; the server already flattens, and MCP/REST callers get the same semantics. |
| **Empty section accepts a moved block** | Relax `moveLeaf` for item/group movers at a section boundary: moving **down** when `entries[b1]` is a section heading → swap the mover's block with **that heading entry only** (`p = [b1, b1+1]`): the mover becomes the section's first row; moving **up** when `entries[b0-1]` is a section heading → swap with that heading only: the mover exits above the heading (first row of section B ↑ → last row of section A, or the leading run). Each is exactly one-step invertible (same swap back). Section-heading movers and options keep today's rules. Drag in the same list past a section li = `delta +1` = enters the section (today: a refused op, nothing happens). | Cross-list drag (`connectWith`, new `moveTo` op, min-height on empty `ul`s): more code, new op, and the stop-handler/`sortable('cancel')` logic assumes one list (`outline.js:651-660`). Can follow later if the owner wants a real drop target. **[OWNER]** this drops the v1 "sections are move limits" rule — see §4. |
| **Insert ▾ → Group heading** | New third entry `Group heading` opening a CONFIRM popup with a name input (default `New group`) and the `Pick one (1)` / `Pick many (N)` radios of the Make-group form (`presets.js:600-642` pattern); one new op **`addGroup {name, cardinality?, after?/before?}`** built by generalising `opAddSection` into `insertHeading(doc, a, rank, gmeta)`: fresh block (`mintIdentifiers`, empty content, `defaultFields()`), rank `group`, gmeta `{name, cardinality, guessed:false}`, ON in the active loadout, false in other roots, same landing rules as `addSection`. Result: a headed empty group; Insert → Block with it selected adds members one by one (chunk 2 rule). Name is stored as typed (group headings have no `== ==` convention). | Two ops `addBlock` + `promote` from the UI: two revisions, two undos — round 1 fixed Insert → Section heading to ONE op for exactly that reason (README:424-427). `createGroup` needs existing members, so it cannot make an empty group. |
| **Make group heading on a section heading** | `headingAction(doc, key, 'group')` with `found.rank === 'section'` returns `{ label: 'Make group heading', op: { op: 'demote', key } }` (replacing the refusal at `outline-model.js:289`); button title: *Turn the section heading into a group heading; its rows stay below it as plain rows — select them and Demote to make them options*. Status line after the op says the same. | Composing `unmakeSection` + `createGroup(rows)`: fails on markers/groups inside the section (`docops.js:493-505`), two revisions, and the owner's actual flow (fresh empty heading) has no rows yet. |
| **Fork UI** | `Fork` button between `Open` and `Load` (`window.js:406-411`); click → `callGenericPopup('Fork name', POPUP_TYPE.INPUT, `${item.name} fork`)`; cancel/blank → nothing; `bridge.edit(() => api('POST', `/presets/${item.id}/fork`, { name }))`; success → `onChange()` then `onOpen(res.doc.id)`; failure (409 taken name, etc.) → the Delete path's `.pm-error` prepend with the server message. No library-side rename-on-conflict. | A folder/tags form: not asked. Auto-suffixing `fork 2` on 409: hides the conflict; the owner can retype. |

## 4. Owner decisions needed (recommended default in bold)
- **Insert placement: after vs before.** Default **after** (reasons in §1). Alternative: keep before, add a "Block inside section" entry — more menu, same asymmetry.
- **Section headings stop being move walls** for items/groups (v1 parity rule, `outline.js:466-480`). Default **yes, one row at a time** (the swap with the heading entry). Alternative: keep the wall and add cross-list drag only — bigger, and `↓`/Alt+↓ would still refuse.
- **`addBlock` after a group option = next option** (joins the group). Default **yes** (mirrors drop ON a heading = first option). Alternative: after the whole group as a plain row.
- **`addGroup` as a new op** (not new schema). Default **yes** (one revision, one undo, matches round 1's one-op rule). Alternative: UI composes `addBlock`+`promote` (two revisions).
